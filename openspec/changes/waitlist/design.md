# Design: Лист ожидания

## Context

Вместимость задаётся на тип билета (`ticket_types.capacity`), проверка мест — в `RegistrationsService.CreateRegistrationAsync` подсчётом регистраций `registered` и `checked_in`. Место освобождается в трёх местах: отмена участником, отмена организатором (`CancelRegistrationAsync`), аннулирование при блокировке участника (`AdminService.BlockUserAsync`). Отмена события освобождать места не должна: очередь при этом тоже отменяется.

## Goals / Non-Goals

**Goals**

- Не терять участников при заполнении бесплатного типа билета.
- Продвигать очередь автоматически и предсказуемо: первый пришёл — первый получил.
- Не менять существующие контракты API и правило «один email — один билет».

**Non-Goals**

- Платные билеты, подтверждение предложения с таймером, ручное управление очередью — см. proposal.md.

## Decisions

### 1. Очередь на тип билета, а не на событие

Вместимость и правило закрытия живут на типе билета, значит и очередь живёт там же. Участник встаёт в очередь на конкретный тип.

**Альтернатива**: очередь на событие с выбором типа при продвижении. Отвергнута: усложняет продвижение и противоречит текущей модели вместимости.

### 2. Автоматический перевод вместо предложения с таймером

При освобождении места первый в очереди сразу становится регистрацией со статусом `registered` и получает письмо-подтверждение. Нет состояния «предложено», нет фоновой задачи истечения.

**Альтернатива**: письмо «место освободилось, подтвердите за 24 часа». Точнее отражает намерение участника, но требует состояния `offered`, таймера, повторного продвижения при истечении и второго письма. Для первой версии функции выбран простой вариант; участник, которому место больше не нужно, отменяет регистрацию как обычно, и место уходит следующему.

### 3. Только бесплатные типы билетов

`waitlist_enabled` можно включить только при `price = 0`. Для платных типов поведение прежнее: 400 при исчерпании. Причина: автоматический перевод не может завершить оплату, а заглушка оплаты не должна создавать «оплаченные» регистрации без действия участника.

### 4. Отдельная таблица `waitlist_entries`

Не расширяем `registrations` статусом `waiting`: у регистрации есть UNIQUE(event_id, email) и бизнес-правила по статусам, которые очередь бы усложнила. Запись очереди хранит те же данные участника, что и регистрация, чтобы продвижение не требовало повторного ввода.

```text
meetup.waitlist_entries
  id             BIGSERIAL PK
  event_id       BIGINT FK events
  ticket_type_id BIGINT FK ticket_types
  user_id        BIGINT FK users NULL       -- NULL для гостей
  email, first_name, last_name, middle_name, phone
  status         VARCHAR(20)  waiting | promoted | cancelled
  created_at     TIMESTAMPTZ                -- порядок очереди
  promoted_registration_id BIGINT FK registrations NULL
  UNIQUE (event_id, email) WHERE status = 'waiting'
```

Порядок очереди — `created_at, id`. Позиция вычисляется запросом, не хранится.

### 5. Продвижение в одной транзакции с освобождением места

`CancelRegistrationAsync` и `BlockUserAsync` после перевода регистрации в `cancelled` вызывают `PromoteFromWaitlistAsync(ticketTypeId)` в той же транзакции: выбрать первую `waiting` запись `FOR UPDATE SKIP LOCKED`, проверить, что место действительно есть, создать регистрацию, пометить запись `promoted`, отправить письмо. Так два одновременных освобождения не продвигают одного и того же участника дважды.

### 6. Правило «один email — один билет» распространяется на очередь

Email, у которого есть активная регистрация на событие, не встаёт в очередь; email в очереди не может зарегистрироваться повторно на другой тип. При продвижении регистрация создаётся с теми же проверками, что и обычная.

### 7. Отмена события очищает очередь

При `cancelled` события все записи `waiting` переводятся в `cancelled`; участники очереди получают то же письмо об отмене, что и зарегистрированные.

## API

| Метод | Endpoint | Изменение |
|---|---|---|
| POST | `/api/v1/events/{id}/registrations` | новый ответ `202 { "status": "waitlisted", "waitlistEntryId": 7, "position": 3 }` при исчерпании мест и `waitlist_enabled = true` |
| DELETE | `/api/v1/waitlist/{id}` | новый: участник выходит из очереди (по email учётной записи) |
| GET | `/api/v1/events/{id}/waitlist` | новый: организатор видит очередь по типам билетов |
| GET | `/api/v1/me/registrations` | в ответ добавляется массив `waitlist` с позицией |
| POST | `/api/v1/events` | у типа билета новое необязательное поле `waitlistEnabled` (по умолчанию `false`; при `price > 0` — 400) |

## Risks / Trade-offs

- Автоматический перевод может создать регистрацию участнику, который уже нашёл другое событие. Смягчение: письмо о переводе содержит ссылку на отмену (для участников с учётной записью) и напоминание обратиться к организатору (для гостей).
- Продвижение внутри транзакции отмены удлиняет её на отправку письма. Смягчение: письмо отправляется после коммита, как и сейчас (`_ = SendAsync`).

## Migration and Rollback

- Скрипт `src/backend/db/012_waitlist.sql` идемпотентен; откат — `012_waitlist_down.sql` (удаление таблицы и колонки), данные очереди при откате теряются, регистрации не затрагиваются.
- Функцию можно отключить без отката схемы: организатор не включает `waitlistEnabled`, поведение прежнее.
