# Research: Чек-ин по QR-коду

## Генерация QR на backend

**Decision**: `QRCoder` (NuGet), `PngByteQRCode`.
**Rationale**: чистый .NET без System.Drawing, работает на Linux, выдаёт PNG в байтах для inline-вложения в письмо и для endpoint.
**Alternatives**: `ZXing.Net` — тяжелее, тянет платформозависимый рендеринг; внешний API — нарушает принцип IV конституции.

## Сканирование в браузере

**Decision**: `html5-qrcode`.
**Rationale**: работает с `getUserMedia`, поддерживает мобильные браузеры, нет серверной части.
**Alternatives**: `@zxing/browser` — сопоставимо, меньше готовых UI-обвязок; нативное приложение — вне scope Phase A.

## Формат токена

**Decision**: 16 случайных байт (`RandomNumberGenerator`) в base64url, 22 символа, колонка `VARCHAR(32) UNIQUE`.
**Rationale**: 128 бит энтропии, короткая строка для ручного ввода, безопасно для URL.
**Alternatives**: UUID v4 — 36 символов, неудобно вводить вручную; HMAC от id — предсказуем при утечке ключа.

## Вложение изображения в письмо

**Decision**: inline-вложение через MailKit `BodyBuilder.LinkedResources` с `cid:`.
**Rationale**: не требует внешнего хостинга картинки; ссылка на `GET /qr` в письме гостю не подходит, у гостя нет учётной записи.
**Alternatives**: ссылка на изображение — требует публичного неавторизованного endpoint с токеном в URL, что расширяет поверхность утечки.

## Ограничение первой версии

Гость без учётной записи получает код только письмом. Если письмо потеряно, организатор отмечает вручную (US3). Восстановление кода для гостей — отдельная функция, зависит от «подтверждение email» (Phase A, следующие фазы).
