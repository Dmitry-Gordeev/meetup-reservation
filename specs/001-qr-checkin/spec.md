# Feature Specification: Чек-ин по QR-коду

**Feature Branch**: `001-qr-checkin`
**Created**: 2026-09-06
**Status**: Draft
**Input**: FR-05.5 (Phase B, «Won't — след. фаза»), Phase A раздел 3.2: «Чек-ин по QR-коду — планируется в следующих фазах (в первой версии — ручная отметка участников)».

## Контекст

Сейчас организатор отмечает участников вручную в списке (`PATCH /api/v1/registrations/{id}/check-in`). На мероприятии с сотнями участников ручной поиск по фамилии на входе создаёт очередь. Функция добавляет уникальный QR-код в подтверждение регистрации и сканирование этого кода организатором на входе. Ручная отметка сохраняется как резервный способ.

## User Scenarios & Testing

### User Story 1 — Участник получает QR-код (Priority: P1)

Участник регистрируется на событие и получает письмо-подтверждение, в котором есть QR-код. Он показывает код с телефона на входе.

**Why this priority**: без кода в письме сканировать нечего; это предусловие для всех остальных историй.

**Independent Test**: зарегистрироваться на событие, открыть письмо в MailHog, убедиться, что в письме есть изображение QR-кода и что закодированное значение совпадает с токеном регистрации в БД.

**Acceptance Scenarios**:

1. **Given** событие активно и есть места, **When** участник регистрируется, **Then** письмо-подтверждение содержит QR-код, а у регистрации в БД сохранён уникальный `qr_token`.
2. **Given** регистрация создана до внедрения функции, **When** участник открывает «Мои регистрации», **Then** для неё тоже доступен QR-код (токен создан миграцией).
3. **Given** зарегистрированный участник открыл «Мои регистрации», **When** он выбирает регистрацию, **Then** видит тот же QR-код, что и в письме.

---

### User Story 2 — Организатор сканирует QR на входе (Priority: P1)

Организатор открывает страницу сканирования события, наводит камеру на код участника, система отмечает чек-ин.

**Why this priority**: основная ценность функции — убрать очередь на входе.

**Independent Test**: отсканировать валидный код — регистрация переходит в `checked_in`, на экране зелёное подтверждение с именем участника; ручная отметка в списке показывает то же состояние.

**Acceptance Scenarios**:

1. **Given** регистрация в статусе `registered`, **When** организатор этого события сканирует её QR-код, **Then** статус становится `checked_in`, `checked_in_at` заполнен, на экране показаны имя и тип билета участника.
2. **Given** регистрация уже `checked_in`, **When** код сканируют повторно, **Then** система отклоняет чек-ин с сообщением «уже отмечен» и временем первого прохода; статус не меняется.
3. **Given** регистрация `cancelled`, **When** код сканируют, **Then** система отклоняет чек-ин с сообщением «регистрация отменена».
4. **Given** код относится к другому событию или другому организатору, **When** его сканируют, **Then** система отвечает «код не найден для этого события» и не раскрывает данные участника.
5. **Given** камера недоступна, **When** организатор вводит код вручную в поле на той же странице, **Then** результат тот же, что при сканировании.

---

### User Story 3 — Ручная отметка остаётся (Priority: P2)

Организатор по-прежнему может отметить участника кнопкой в списке, если у того нет кода.

**Independent Test**: отметить участника кнопкой в списке; затем отсканировать его код — получить «уже отмечен».

**Acceptance Scenarios**:

1. **Given** участник отмечен вручную, **When** сканируют его код, **Then** ответ «уже отмечен».

### Edge Cases

- Токен угадать нельзя: 128 бит случайности, без последовательности.
- Один и тот же email на двух событиях — два разных токена.
- Письмо не доставлено: код доступен в «Мои регистрации» для участников с учётной записью; гость может обратиться к организатору для ручной отметки.
- Экспорт участников включает статус чек-ина как раньше; токен в экспорт не попадает.

## Requirements

### Functional Requirements

- **FR-001**: Система MUST создавать уникальный непредсказуемый `qr_token` для каждой регистрации при её создании.
- **FR-002**: Система MUST заполнить `qr_token` для всех существующих регистраций миграцией, без ручных действий организаторов.
- **FR-003**: Письмо-подтверждение регистрации MUST содержать QR-код, закодированное значение — `qr_token`.
- **FR-004**: Система MUST предоставлять организатору события endpoint чек-ина по токену; чек-ин возможен только для регистраций этого события.
- **FR-005**: Повторное сканирование MUST отклоняться без изменения статуса и с указанием времени первого чек-ина.
- **FR-006**: Сканирование кода отменённой регистрации MUST отклоняться.
- **FR-007**: Организатор MUST иметь страницу сканирования с камерой и полем ручного ввода кода.
- **FR-008**: Зарегистрированный участник MUST видеть QR-код своей регистрации в «Мои регистрации».
- **FR-009**: QR-изображение MUST генерироваться внутри backend; внешние сервисы генерации не используются.
- **FR-010**: Существующий endpoint ручного чек-ина MUST продолжать работать без изменений контракта.

### Key Entities

- **Registration** — регистрация участника; получает атрибут `qr_token` (уникальный, непредсказуемый, неизменяемый).
- **Check-in by QR** — действие организатора: событие + токен → регистрация `checked_in` либо отказ с причиной.

## Success Criteria

- **SC-001**: Чек-ин одного участника по QR занимает не более 3 секунд от сканирования до подтверждения на экране.
- **SC-002**: 100 % регистраций, созданных после внедрения, имеют QR-код в письме (проверка по MailHog в ручном тесте).
- **SC-003**: Повторное сканирование никогда не создаёт второй чек-ин: `checked_in_at` не меняется.
- **SC-004**: Чек-лист `docs/testing-checklist.md` дополнен разделом FR-05.5 и проходит целиком.

## Assumptions

- Устройство организатора — телефон или ноутбук с камерой и современным браузером; доступ к камере требует HTTPS в production.
- QR-код в письме — встроенное изображение (inline PNG); почтовые клиенты, блокирующие изображения, показывают текстовый код рядом.

## Out of Scope

- Офлайн-режим сканера, печать бейджей, чек-ин через SMS, чек-ин администратором платформы, статистика посещаемости.
