# Чеклист полного SDD-процесса

SDD (Spec-Driven Development) — разработка от спецификации. Этот чеклист помогает команде или разработчику спроектировать процесс работы с требованиями и проверить его полноту: от определения задачи до реализации и обновления документации.

Проходите этапы последовательно, фиксируя решения в общих артефактах. Между этапами допускаются возвраты и уточнения. Согласованность требований проверяется на протяжении всего цикла. Для неприменимых пунктов указывайте причину; глубину проработки выбирайте с учётом масштаба задачи и рисков.

## 0. Определить точку входа

- [ ] Для нового проекта определить принципы, видение и границы.
- [ ] Для существующей системы провести инвентаризацию текущих возможностей, данных, API и контрактов, компонентов, ограничений и критичных сценариев.
- [ ] Сверить описание существующей системы с кодом и рабочими контрактами.
- [ ] Зафиксировать текущее состояние как базовую линию для будущих изменений.

## 1. Правила и общий контекст

Зафиксировать переиспользуемые договорённости:

- [ ] Правила репозитория и разработки.
- [ ] Архитектурные принципы.
- [ ] Допустимые технологии.
- [ ] Требования к тестам.
- [ ] Соглашения по API, данным, ревью и поставке.
- [ ] Правила изменения API и базы данных.
- [ ] Требования безопасности и регуляторики.
- [ ] Ограничения для ИИ-агента.

Возможные артефакты: `AGENTS.md`, `CLAUDE.md`, правила проекта, инструкции агентам, общие навыки проверки.

## 2. Видение и границы

Описать, зачем создаётся изменение и каким должен быть результат:

- [ ] Цель и ожидаемая ценность.
- [ ] Стейкхолдеры и пользователи.
- [ ] Границы задачи.
- [ ] Явные исключения и функции вне объёма.
- [ ] Критерии завершения.
- [ ] Критерии приёмки.
- [ ] Ограничения, которые нельзя нарушать.

Возможные артефакты: `vision.md`, `proposal`.

## 3. Бизнес-архитектура и возможности

Описать, что система должна уметь, независимо от реализации:

- [ ] Карта бизнес-возможностей (`Capability Map`).
- [ ] Иерархия возможностей.
- [ ] Роли пользователей.
- [ ] Пользовательские истории.
- [ ] Сценарии с условиями и ожидаемыми результатами.
- [ ] Ценность каждого сценария.
- [ ] Проверяемые требования.

Возможности не подменяются списком экранов, API-методов или задач разработки.

Возможные артефакты: `capabilities.md`, `stories.md`, спецификации возможностей.

## 4. Архитектура информационных систем

Описать логическое устройство решения:

- [ ] Модель и структура данных.
- [ ] Приложения и компоненты.
- [ ] API и интеграционные контракты.
- [ ] Зависимости между компонентами.
- [ ] Связи данных и API с пользовательскими сценариями.
- [ ] Правила миграций, если они уже известны.
- [ ] Существующие контракты, которые требуется сохранить.

Технологии можно пока описывать абстрактно: например, «брокер сообщений», без выбора конкретного продукта.

## 5. Технологическая архитектура

Зафиксировать конкретную техническую среду:

- [ ] Платформа и инфраструктура.
- [ ] Способы развёртывания.
- [ ] Стандарты и технические ограничения.
- [ ] Безопасность.
- [ ] Совместимость.
- [ ] Допустимые технологии.
- [ ] Причины выбора технологий.
- [ ] Последствия и риски выбранных решений.

Возможные артефакты этапов 4–5: `contracts/`, `constraints.md`, схемы, OpenAPI, записи архитектурных решений (ADR), предложения изменений для обсуждения (RFC) и связанные документы.

## 6. Проверка целевой архитектуры

До составления плана реализации проверить весь накопленный контекст:

- [ ] Каждая возможность в границах изменения покрыта хотя бы одним сценарием.
- [ ] Каждый сценарий относится к существующей возможности.
- [ ] Данные и API поддерживают сценарии.
- [ ] Компоненты не нарушают ограничения.
- [ ] Границы и исключения соблюдаются.
- [ ] Критерии приёмки проверяемы.
- [ ] Новая модель совместима с текущим состоянием системы.
- [ ] Нет конфликтов между требованиями, архитектурой и контрактами.
- [ ] Решения по найденным конфликтам приняты людьми и отражены в связанных артефактах.

## 7. Варианты решения и целевое состояние

Сформировать путь от текущего состояния к целевой архитектуре:

- [ ] Возможные варианты реализации.
- [ ] Выбранный вариант.
- [ ] Отвергнутые варианты и причины отказа.
- [ ] Целевое состояние.
- [ ] Влияние на существующую систему.
- [ ] Совместимость.
- [ ] Миграции.
- [ ] Стратегия отката.
- [ ] Риски и приемлемый уровень изменений.

Архитектурные решения и их причины сохраняются в ADR или RFC.

## 8. План перехода и пакеты работ

Разбить переход на проверяемые части:

- [ ] Последовательность этапов.
- [ ] Зависимости.
- [ ] Задачи, выполняемые параллельно.
- [ ] Задачи, требующие строгого порядка.
- [ ] Критерии готовности каждого пакета.
- [ ] Контрольные точки.

Каждый пакет работ — небольшой контракт на одну итерацию:

- [ ] Входные артефакты и зависимости.
- [ ] Ожидаемый результат.
- [ ] Критерии приёмки.
- [ ] Контракты, которые нельзя сломать.
- [ ] Проверки.
- [ ] Способ отката или безопасной миграции.

После разбиения:

- [ ] Проверено, что выполнение пакетов приводит к целевой архитектуре.
- [ ] Команда согласовала порядок, параллельность и риск.

## 9. Реализация и контроль соответствия

Агент или разработчики выполняют пакеты работ:

- [ ] Изменяют код, конфигурацию и данные.
- [ ] Реализуют API и интеграции.
- [ ] Выполняют миграции.
- [ ] Запускают тесты и статические проверки.
- [ ] Проверяют контракты.
- [ ] Выполняют критерии приёмки.
- [ ] Фиксируют прогресс по задачам.
- [ ] При необходимости применяют предусмотренную стратегию отката.
- [ ] Проверяют результат после каждого пакета.

## 10. Финальная проверка и сходимость

Сверить результат с исходными артефактами:

- [ ] Требованиями.
- [ ] Пользовательскими историями.
- [ ] Картой возможностей.
- [ ] Архитектурным решением.
- [ ] Планом и задачами.
- [ ] Критериями приёмки.
- [ ] Тестами и контрактами.
- [ ] Устранить расхождения: исправить код либо явно согласовать изменение требований и обновить спецификацию.

## 11. Актуализация архитектуры и история изменений

При завершении изменения и после проверки поставленного результата:

- [ ] Перенести согласованные изменения в описание текущего состояния.
- [ ] Обновить возможности, данные, API и ограничения.
- [ ] Сохранить принятые решения и причины.
- [ ] Заархивировать завершённое изменение.
- [ ] Оставить историю: что изменили, зачем, почему и каким способом.
- [ ] Зафиксировать результат развёртывания и возможность отката.

Описание текущего состояния должно отражать работающую систему. При обновлении документации отделяйте уже реализованные изменения от запланированных, сохраняйте причины решений и историю завершённых работ.

Названия файлов — примеры. Важны содержание, связи и актуальность артефактов.

## Сквозные правила процесса

- [ ] Определён единый источник истины.
- [ ] Границы, исключения и ограничения описаны явно.
- [ ] Поддерживаются связи «цель → возможность → сценарий → данные/API → ограничение».
- [ ] Для каждого артефакта понятно, зачем он нужен и что по нему проверяется.
- [ ] Разделы заполняются последовательно; вопросы и ответы фиксируются в спецификации.
- [ ] После каждого крупного раздела проверяется вся накопленная цепочка.
- [ ] До плана перехода и написания кода предусмотрена проверка целевой архитектуры.
- [ ] После составления плана проверяется его соответствие целевой архитектуре.
- [ ] Решения по конфликтам принимает человек.
- [ ] История решений и изменений сохраняется.
- [ ] Все этапы выбранной структуры представлены: для неприменимого этапа явно указаны статус и причина.
- [ ] Существующие RFC, ADR, OpenAPI, Storybook и другие документы включены в общий контекст.
- [ ] Глубина проработки выбрана осознанно с учётом масштаба задачи и стоимости поддержки.
